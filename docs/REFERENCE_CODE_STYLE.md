# Reference code style

AlgoViz 的三语言参考代码同时承担“可运行实现”和“教学材料”两个职责。C/C++/Python 文件都必须遵守本约定。

## Formatting

- C/C++ 使用 Allman 大括号：函数、`if`、`for`、`while`、`struct`、`class` 的左大括号另起一行。
- 统一四空格缩进，不使用 Tab；行宽上限 100。Python 使用 4 空格缩进和标准库风格。
- **不要用空行填充版面**。空行只用于：文件头与代码之间、函数之间、不相关的逻辑块之间。大括号内第一行、`return` 前、连续赋值之间、单条语句之后都不要额外加空行。
- 仓库根目录的 `.clang-format` 固化大括号与缩进规则：

```powershell
clang-format -i --style=file path\to\file.c path\to\file.cpp
```

## Comment density

参照教材 Kosaraju 参考实现的三层粒度，不逐行翻译代码，也不写“给 i 加一”这类显而易见的注释。

### 1. 文件/模块头

每个文件必须有中文文件头，依次说明：

1. **用途与整体思路**：这份实现解决什么问题，核心步骤是什么。
2. **阅读顺序**：先看哪个结构/函数，再看哪条分支。
3. **输入与输出**：数据类型、返回含义、失败与边界行为。
4. **关键不变量**：循环或递归中始终成立的事实，例如下标范围、长度含义、颜色/高度/距离定义。
5. **易错点**：下标混用、边界取等、初始化顺序、资源释放、空输入等。
6. **复杂度**：时间与额外空间，注明最坏/平均/最好及原因。

小文件可以把“函数地图”并入文件头，逐行列出每个函数接收什么、返回什么、改哪些状态；复杂文件仍应在每个函数前写独立函数头。

### 2. 函数头

每个非平凡函数都要写清：

- **职责**：一句话说明它完成什么，而不是重复函数名。
- **参数**：每个参数的含义、范围、所有权；数组/链表/图要说明长度、哨兵或边界。
- **返回值**：成功、失败、空输入分别返回什么；`void` 明说“无返回值”。
- **副作用**：修改哪些字段/结构、是否分配或释放内存、是否写标准输出。
- **前置条件与不变量**：调用前必须成立什么，函数返回时保证什么。

构造函数、只读打印函数可以压缩成一行，但不能只写“构造函数”或“打印”。

### 3. 关键块与关键行

只在读者容易走错的地方解释“为什么”：

- 指针重接的顺序，以及交换顺序为什么会断链；
- 下标回绕、边界取等、哨兵值、`-1`/`0` 的区别；
- 递归回退后为什么还要继续修复；
- 旋转、分裂、合并后为什么先更新高度/父指针；
- 方向映射（无向图双边、反向图翻转）；
- 资源释放、失败回滚、输出格式。

不注释 `#include`、`return 0`、显而易见的赋值和逐行翻译。注释必须与实现同步；约定改变时，文件头、函数头和行内注释一起改。

### 4. Python 约定

Python 用模块 docstring 承载文件头，用函数 docstring 承载职责、参数、返回、异常和副作用。模块头必须包含中文导读、阅读顺序、输入/输出、不变量、易错点和复杂度；每个非平凡函数前用一行 `# 作用：...` 点明职责、参数含义和返回/异常，再保留原有 docstring 细节。空模式串、空输入等边界必须与实现一致；不能写“返回空列表”而实际抛 `ValueError`。

C/C++ 的每个非平凡函数前同样要有一行 `# 作用` 对应的中文职责说明；参数较多时在其下方补“参数/返回/副作用”，但不得为了排版插入空行。

## Verification

新增或修改参考代码后，至少执行：

```powershell
clang-format -i --style=file <changed .c/.cpp files>
gcc -std=c11 -Wall -Wextra <file>.c -o <tmp>.exe
g++ -std=c++17 -Wall -Wextra <file>.cpp -o <tmp>.exe
python <file>.py
npx vitest run src/domain/reference-code
```
