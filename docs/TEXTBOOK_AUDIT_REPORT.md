### 2.2 P0 详情

#### P0-01：`circular` 参考实现忽略分配失败并在 `main` 中解引用空 `tail`

- **严重程度**：P0（明确非法内存访问风险；仅 OOM 触发，不是当前正常运行的崩溃）
- **所属章节**：第 2 章线性表参考代码，校准样本
- **课程 / 名称**：`circular` 循环链表
- **文件**：
  - `src/domain/reference-code/sources/circular/circular_linked_list.c:116–127`
  - `src/domain/reference-code/sources/circular/circular_linked_list.cpp:120–129`
- **相关函数 / 组件**：`list_append` / `append`、`main`、`list.tail` / `list.tail()`
- **具体位置 / 代码范围**：
  - C：`main` 连续调用 3 次 `list_append`，不检查返回值；随后执行 `list.tail->next->value`。
  - C++：`main` 连续调用 3 次 `append`，不检查 `bool` 返回值；随后执行 `list.tail()->next->value`。
- **复现步骤或输入**：
  1. 用会令第一次 `malloc` / `new (std::nothrow)` 返回 `NULL` 的分配器编译并运行该示例；
  2. 第一次 `list_append` / `append` 返回 `false`，`list.tail` 仍为 `NULL`；
  3. `main` 无条件读取 `list.tail->next` / `list.tail()->next`。
- **预期行为**：`main` 检查每次插入的返回值；任一失败时立即输出错误并返回非 0，或在解引用前确认 `tail != NULL`。
- **实际行为**：忽略返回值；第一次分配失败时直接解引用空指针，进程崩溃。
- **对学生学习或程序运行的影响**：这是学生最可能直接复制到作业中的参考实现；把“演示程序”写成不处理失败路径，会传递错误的 API 使用习惯。
- **初步根因**：`main` 只演示成功路径；API 已经用布尔返回值表达失败，但调用方没有消费该契约。
- **建议修复方向**：在 `main` 中逐次检查返回值，失败即 `return EXIT_FAILURE`；或在进入打印前做 `tail != NULL` 保护。不要用 `assert` 代替运行时错误处理。
- **建议回归测试**：增加一个失败注入构建（第一次 `malloc`/`new` 返回 `NULL`），运行 `main` 应正常退出而非崩溃；同时用 `clang --analyze` / `g++ -fanalyzer` 做静态检查。

| 注释事实错误 | “静态函数”但无 static；结构体无 length 却写 length；`linked` 头文件声称 tail/尾插；Python `main` 声称头插/删除但未实现 | P1-12 |
| 关键教学解释缺失 | `do-while` 为何在回到 head 停止；`free` 前为何保存 next；失败返回值为何必须检查 | P1-13 / P0-01 |
| 模板化与冗余 | 167 个文件 1337 行 `Purpose` + `作用`；简单函数重复签名信息 | P2-06 |
| 双语不一致 | 27 个文件无 annotation；中文导读模板未按文件替换；Python 注释密度显著低 | P2-05 |
| 代码安全 / 正确性 | `circular` C/C++ `main` 忽略 append 失败，OOM 空指针解引用 | P0-01 |

### 6.2 校准样本逐项结论

| 检查项 | 结果 |
|---|---|
| 文件头介绍未实现的操作 | 存在：`linked.c` 头文件声称 tail/length/尾插；Python `circular` main 注释声称头插/尾插/删除 |
| 注释提到结构体中不存在的 length | 存在：`circular.c/.cpp`、`doubly.c/.cpp` |
| 注释称存在“静态函数”但函数未 static | 存在：54 个 C/C++ 文件；5 个新算法文件已确认 |
| `list_append` 的关键指针维护说明 | 部分存在：英文导读说明了“新结点指向 head、旧 tail 指向新结点”的顺序；中文“作用”只讲结果，未讲清失败时 `tail` 不变以及为什么最后才更新 `tail` |
| `list_print` 没讲透 `do-while` 终止原因 | 存在：只讲“只读遍历”，未讲回到 head 停止、空表提前返回 |
| `list_free` 没讲透释放前保存后继 | 存在：只说“注意环的终止条件”，未讲释放后不能再读 `node->next` |
| `main` 未检查分配失败后的访问风险 | 存在：C/C++ 均忽略 3 次插入返回值，随后解引用 `tail`/`tail()` |

### 6.3 C/C++/Python 差异

| 语言 | 非 convenience 文件数 | 平均总行数 | 平均注释行 | 平均中文注释行 |
|---|---:|---:|---:|---:|
| C | 60 | 143.6 | 31.8 | 12.7 |
| C++ | 60 | 133.0 | 31.0 | 11.7 |
| Python | 60 | 93.1 | 12.6 | 7.1 |

Python 的注释密度低不必然是缺陷，因为 Python 代码更短；但关键状态转换的解释明显少于 C/C++，需要按“关键函数覆盖”而不是“注释行数”补。

### 6.4 注释审计标准

本轮的判断标准是“初学者能否通过注释理解关键算法设计”，不是注释总行数：

- 不要求给简单赋值、循环变量自增、显而易见的 `return` 逐行加注释；
- 要求解释循环不变量、递归终止条件、指针重接顺序、失败路径、复杂参数和副作用；
- 要求中英文注释语义等价，而不是逐字直译；
- 要求文件头与结构体/函数签名一致，不能介绍不存在的字段或函数类别；
- 代码正确性问题与注释质量问题分开登记，不把“能编译”当作注释合格。
